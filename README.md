# KOPO Course Finder

한국어 자연어 질문으로 **한국폴리텍대학 서울정수캠퍼스의 역대 개설강좌를 조회하고, 이전 조회의 맥락을 이어서 질문**하는 프로젝트입니다. Gemini API가 맥락이 필요한 후속 질문을 독립적인 조회 질문으로 재작성하고, 로컬 Text-to-SQL 모델이 SQL을 생성합니다. 실제 데이터베이스 조회 결과를 표·실행한 SQL·조건 기반 자동 안내로 보여줍니다.

> 엑셀 적재, 로컬 모델 조회, Gemini 질문 재작성·세션 관리, Gradio 화면을 구현했습니다. 실제 44개 파일·7,507개 강좌와 RTX 3080에서 로컬 조회를 확인했습니다. Gemini는 SDK의 모의 HTTP 응답으로 연결·실패 처리를 검증했으며, 실제 키를 이용한 재작성 품질·모델 접근 권한 확인은 남아 있습니다. 결과 안내는 외부 API 없이 생성합니다.

## 프로젝트 배경

학기·학년별로 나뉜 개설강좌 스프레드시트에서 여러 학기의 강좌를 비교하려면 파일을 하나씩 열어 확인해야 합니다. 이 프로젝트는 해당 자료를 하나의 관계형 데이터베이스로 모아, SQL을 모르는 사용자도 질문으로 필요한 강좌를 찾을 수 있도록 합니다.

수강신청을 앞둔 재학생과 학과의 교육과정을 미리 확인하고 싶은 입학 예정자·신입생을 주요 사용자로 생각하고 있습니다.

## 질문 예시

- "2025년 1학기 인공지능소프트웨어과 2학년 강좌를 보여줘."
- "과목명에 '파이썬'이 들어가는 강좌를 찾아줘."
- "2025년 1학기 학과별 강좌 수를 알려줘."
- "2025년 1학기 학과별 서로 다른 과목 수를 알려줘."
- "연도별 NCS 강좌 비율을 보여줘."
- "2025년 인공지능소프트웨어과의 모든 개설강좌를 알려줘." → "이전 결과에서 NCS 강좌만 남겨줘." → "그중 2학기만 보여줘."

조회 가능한 학년도·학기와 학과는 실제 적재된 자료를 기준으로 안내할 예정입니다.

## 구현할 기능

| 구분 | 기능 | 내용 |
| --- | --- | --- |
| 필수 | 데이터 적재 | 개설강좌 `.xlsx` 파일의 형식을 확인하고 정제·가명 처리한 뒤 SQLite에 적재 |
| 필수 | 자연어 강좌 조회 | 한국어 질문을 SQL로 변환하고 검증 후 실행하여 결과 표 표시 |
| 필수 | 실행한 SQL 확인 | 조회에 사용한 SQL을 화면에서 확인 |
| 필수 | 조건 기반 자동 결과 안내 | 조회 행 수, 집계 값, 빈 결과, 표시 제한, 처리 상태·오류를 로컬 규칙과 템플릿으로 안내 |
| 필수 | Gemini 질문 재작성 | 이전 질문·조회 정보를 참고해 후속 질문을 독립적인 조회 질문으로 변환 |
| 필수 | 대화 맥락 관리 | 세션별 검색 기록, 조건 누적·변경, 새 주제 전환, 모호한 질문 되묻기, 대화 초기화 |
| 필수 | 예시 질문과 질문 확인 | 예시 질문 버튼과 사용자 원문·재작성된 질문 표시 |
| 선택 | 결과 다운로드 | 조회 결과를 CSV로 저장 |

Gemini를 이용한 후속 질문 처리는 핵심 구현 범위입니다. 다만 API 키가 없거나 호출에 실패해도 독립적인 질문의 기본 조회와 자동 결과 안내는 제공합니다. 맥락 해석이 필요한 질문에는 조건을 모두 포함해 다시 입력하도록 안내하며, 해석하지 못한 질문을 그대로 SQL 모델에 보내지 않습니다. CSV 다운로드는 핵심 조회·대화 기능 검증 이후의 선택 기능입니다.

## 처리 흐름

```text
개설강좌 엑셀 파일
    └─ 형식 확인 → 정제·가명 처리 → SQLite 적재

한국어 질문
    ↓
입력 확인 및 세션 맥락 확인
    ├─ 독립적인 질문: 원문 사용, Gemini 호출 없음
    └─ 맥락이 필요한 후속 질문: Gemini로 질문 재작성 (최대 1회)
        └─ 맥락 부족·모호함·API 실패: 안내 후 대기, SQL 생성 안 함
    ↓ 질문이 확정된 경우
SQL 프롬프트 구성
(독립적인 조회 질문 + DB 스키마 + 한국어 컬럼 설명 + 수집 범위 + 학과명 목록)
    ↓
로컬 Text-to-SQL 모델로 SQL 생성
    ↓
SQLGlot 검증 → 읽기 전용 SQLite 조회
    ↓
결과 표 + 실행한 SQL + 원문/재작성 질문 + 조건 기반 자동 안내
    ↓
성공한 조회 정보를 세션에 보관 → 다음 질문에 활용
(결과 안내 단계의 Gemini 호출 없음)
```

모델은 greedy decoding으로 SQL 생성의 무작위성을 줄이고, 조회 결과의 근거가 되는 SQL을 화면에 표시할 계획입니다. 다만 실행 가능한 SQL도 질문의 의도와 다를 수 있으므로, 평가 질문과 정답 SQL로 조회 정확도를 검증할 예정입니다.

### 대화 맥락과 API 사용 정책

| 사용자 입력 | Text-to-SQL 모델에 전달할 질문 |
| --- | --- |
| 2025년 인공지능소프트웨어과의 모든 개설강좌를 알려줘 | 2025년 인공지능소프트웨어과의 모든 개설강좌를 알려줘 |
| 이전 결과에서 NCS 강좌만 남겨줘 | 2025년 인공지능소프트웨어과의 개설강좌 중 NCS 강좌만 알려줘 |
| 그중 2학기만 보여줘 | 2025년 2학기 인공지능소프트웨어과의 NCS 개설강좌를 알려줘 |
| 그럼 2024년은? | 2024년 2학기 인공지능소프트웨어과의 NCS 개설강좌를 알려줘 |

- 첫 질문이나 새 조회에서 맥락 없이 해석할 수 있는 질문은 Gemini를 호출하지 않습니다. 이전 맥락 없이 "그중" 등을 물으면 조건을 되묻습니다.
- 맥락 의존 여부가 불분명하면 임의로 조건을 합치지 않고 Gemini로 해석합니다. 필요한 조건이나 지칭 대상이 여전히 모호하면 조회 전에 되묻습니다.
- 질문 한 번에 Gemini 호출은 최대 1회이며, 결과 해설·SQL 생성·자동 API 재시도에는 사용하지 않습니다. SQL 검증 실패 시의 1회 재생성은 로컬 모델만 사용합니다.
- 전송 맥락은 최근의 필요한 질문, 이전 재작성 질문·조건, 성공한 SQL, 결과 열·집계 값·표시 제한 여부 등으로 제한합니다. 전체 대화와 전체 결과 표를 매번 보내지 않으며, 특정 결과 참조에 필요한 경우에만 소량의 가명 처리된 행을 추가합니다.
- 세션별로 맥락을 분리하고 실패한 조회를 마지막 성공 결과로 덮어쓰지 않습니다. 새 주제에는 이전 조건을 자동으로 물려주지 않으며, "대화 및 결과 초기화"로 맥락을 비울 수 있습니다.
- 후속 필터·개수 질문은 이전 검색 조건 전체를 대상으로 다시 조회합니다. 화면의 200행 표시 제한을 검색 조건으로 이어받지 않습니다.

### 조건 기반 자동 결과 안내

| 상황 | 안내 기준 |
| --- | --- |
| 일반 목록 조회 | 잘리지 않은 결과의 실제 반환 행 수를 안내 |
| 집계 조회 | SQL이 반환한 강좌 수·과목 수·비율 등을 정해진 형식으로 표시. 집계 결과 1행을 강좌 1개로 설명하지 않음 |
| 결과 없음 | "조건에 맞는 강좌가 없습니다"와 조건 수정 안내 |
| 200행 표시 제한 | 200행까지만 표시했음을 안내. 별도 전체 집계 없이 전체 건수를 단정하지 않음 |
| 처리 중·오류·미지원 항목 | 처리 상태와 실패 원인에 대응하는 고정 안내 문구 표시 |

자동 안내는 실제 조회 값과 처리 상태만 사용합니다. 결과의 의미나 경향에 대한 AI 해설은 구현 범위에서 제외합니다.

## 공통 개발 환경

실습실의 Windows + WSL2 + Docker Desktop + RTX 3080 10GB 환경을 기준으로 합니다. 컨테이너는 Linux x86_64, Python 3.11.14, PyTorch 2.6.0 + CUDA 12.4를 사용합니다.

- Docker 빌드·GPU 설정·볼륨·포트는 **`compose.yaml` 하나**에서 관리합니다. 별도 Dockerfile이나 CPU/GPU 오버라이드 파일은 사용하지 않습니다.
- Python의 실행·GPU 추론·개발 도구 의존성은 **`requirements.txt` 하나**에서 관리합니다. 상단에는 직접 사용하는 패키지를 용도별로, 하단에는 전이 의존성을 고정해 정리합니다.
- `.dockerignore`는 빌드에 `requirements.txt`만 허용합니다. 소스와 로컬 데이터는 실행 시 작업 폴더를 연결해 사용합니다.
- `.env`는 필요한 설정을 바꿀 때 사용하며, API 키는 포함하지 않습니다.

빌드 정의를 Compose에 넣는 방식은 [Docker Compose의 `dockerfile_inline`](https://docs.docker.com/reference/compose-file/build/#dockerfile_inline)을 사용하므로 Compose 2.17 이상이 필요합니다. Docker Desktop은 WSL2 기반 Linux 컨테이너와 GPU 지원이 활성화되어 있어야 합니다.

### VS Code에서 개발하기

1. Docker Desktop을 실행하고 VS Code에 [Dev Containers 확장](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-containers)을 설치합니다.
2. VS Code에서 이 저장소 폴더를 엽니다.
3. `Ctrl+Shift+P` → **Dev Containers: Reopen in Container**를 실행합니다.
4. 컨테이너 준비와 확장 설치가 끝나면 통합 터미널에서 개발합니다. Python은 `/usr/local/bin/python`을 사용하며, 호스트 Python이나 별도 가상 환경은 필요하지 않습니다.

`.devcontainer/devcontainer.json`은 기존 `compose.yaml`의 `app` 서비스를 사용합니다. GPU·작업 폴더·모델 캐시·포트 설정도 동일하게 적용됩니다. Python, Pylance, Python Debugger, Ruff, EditorConfig 확장을 자동 설치하고, Python 파일 저장 시 컨테이너에 설치한 Ruff로 포맷·수정·import 정리를 수행합니다. 컨테이너를 처음 만들 때는 `pip check`로 설치 상태를 확인합니다.

실습실에 설치된 Dev Containers CLI 0.90은 `dockerfile_inline`을 직접 해석하지 못하므로, 연결 전에 루트 Compose 파일로 이미지를 빌드하고 `.devcontainer/compose.yaml`이 해당 이미지를 사용하도록 연결합니다. 빌드 내용과 GPU·볼륨·포트 정의는 루트 `compose.yaml`에서 관리하며, VS Code용 파일에는 이미지 연결 설정만 둡니다. 기존 이미지와 빌드 캐시를 재사용합니다.

연결된 VS Code 터미널에서는 `python`, `ruff` 등을 바로 실행합니다. VS Code 창을 닫으면 해당 Compose 서비스를 중지하며, 작업 파일과 모델 캐시는 유지됩니다. `requirements.txt`나 컨테이너 설정을 변경한 뒤에는 **Dev Containers: Rebuild Container**로 반영합니다. 앱 실행과 브라우저 접속 방법은 아래와 같습니다.

### 환경 시작

저장소 루트에서 실행합니다. 별도 설정이 없으면 `.env` 없이도 기본값을 사용합니다. 기존 `.env`가 있다면 새 `.env.example`의 설정과 비교해 필요한 항목만 갱신합니다.

```powershell
docker compose config --quiet
docker compose up -d --build
docker compose exec app bash
```

새 로컬 설정 파일이 필요한 경우에만 `.env.example`을 `.env`로 복사합니다. 기존 `.env`는 덮어쓰지 않습니다.

현재 컨테이너는 개발 작업을 위해 대기하며, 웹 서버를 자동 실행하지 않습니다. 엑셀 적재 후 다음 명령으로 화면을 실행합니다. 모델 로딩을 마치면 접속할 수 있습니다.

```powershell
docker compose exec app python app.py
```

실행 후 접속 주소는 `http://127.0.0.1:7860`입니다. 호스트에는 루프백 주소로만 포트를 열고, 컨테이너 내부의 Gradio는 `0.0.0.0:7860`에서 연결을 받도록 설정했습니다.

### 환경 확인과 종료

```powershell
docker compose exec app python -m pip check
docker compose exec app python -c "import torch; print(torch.__version__, torch.version.cuda); print(torch.cuda.get_device_name(0))"
docker compose exec app ruff check .
docker compose down
```

의존성을 변경했을 때는 이미지를 다시 빌드합니다. Python 소스 수정은 연결된 작업 폴더에 바로 반영되며, 실행 중인 앱의 재시작은 별도로 필요합니다. Hugging Face 모델 캐시는 이름 있는 볼륨에 보관되므로 일반적인 `docker compose down` 후에도 유지됩니다.

현재 환경에서 이미지 빌드, `pip check`, GPU 인식, NF4 4bit 연산, Gradio·Gemini SDK import와 모델 캐시 쓰기를 확인했습니다. 고정 리비전의 기반 모델·어댑터 다운로드와 실제 8B 모델의 반복 SQL 생성도 확인했습니다. Gemini API 키는 화면에서 입력받으며 로컬 환경 파일에는 저장하지 않습니다.

### Gradio 화면과 후속 질문

1. 질문을 입력하거나 예시를 선택하고 **조회**를 누릅니다. 독립 질문은 Gemini 키 없이 처리합니다.
2. **Gemini 후속 질문 설정**을 펼쳐 키를 입력하고 **키 적용**을 누릅니다. 입력칸은 비워지고 키는 해당 세션의 서버 메모리에만 남습니다. 적용 버튼은 키를 저장할 뿐 외부 API를 호출하지 않습니다.
3. 성공한 조회 뒤 `이전 결과에서 NCS 강좌만 남겨줘`, `그중 2학기만 보여줘`처럼 질문합니다. 원문과 실제 SQL 모델에 전달한 독립 질문을 화면에서 비교할 수 있습니다.
4. 모호하면 확인 질문을 표시하고 조회하지 않습니다. 확인 질문에 답하는 중 다른 검색을 시작하려면 **새 조회**를 선택합니다.
5. **대화 및 결과 초기화**는 질문·결과·성공 맥락·대기 중인 확인 요청을 지웁니다. 키는 유지합니다. **키 해제**는 키만 제거하며 독립 질문은 계속 사용할 수 있습니다. 검색 기록의 지우기 버튼도 같은 대화 초기화 처리를 합니다.

`conversation.py`는 명확한 독립 질문을 로컬 규칙으로 구분하고, 맥락이 필요하거나 불분명한 질문에만 Gemini를 요청합니다. 이전 맥락이 없는 지칭 표현에는 API와 SQL 모델 모두 호출하지 않고 조건을 되묻습니다. 규칙 기반 구분이 모든 한국어 표현을 정확히 분류하는 것은 아닙니다.

Gemini 요청은 현재 질문, 마지막 성공한 독립 질문·조건·SQL, 열 이름·표시 행 수·잘림 여부, 필요한 소규모 집계 값과 대기 중인 확인 요청으로 제한합니다. JSON 맥락은 최대 12,000자이며 일반 결과 행과 전체 대화는 전송하지 않습니다. 특정 행을 지칭하지만 제공된 맥락으로 식별할 수 없으면 되묻도록 지시합니다. 화면의 200행 제한은 검색 SQL에 넣지 않으므로 후속 개수 질문도 원래 조건 전체를 집계합니다.

설치된 Google Gen AI SDK의 기본 재시도를 `HttpRetryOptions(attempts=1)`로 끄고, 질문당 `generate_content`를 최대 한 번 호출합니다. 요청 시간 제한은 20초입니다. JSON 응답의 동작·필수 필드·길이·SQL 혼입·미해결 지칭 표현을 검증한 뒤 자연어 질문만 로컬 모델에 넘깁니다. 키 없음, 권한·한도·연결 오류, 응답 형식 오류이면 SQL을 생성하지 않고 마지막 성공 결과를 유지합니다. 화면에 남아 있는 표가 이전 성공 결과임을 별도로 안내합니다.

`summary.py`는 목록 행 수, 단일 COUNT의 강좌·과목 수, 집계 값, 빈 결과, 표시 제한을 로컬에서 안내합니다. COUNT 값 0을 결과 1행 또는 강좌 1개로 설명하지 않습니다. 화면에는 질문별 Gemini 호출 시도 횟수와 처리 상태도 표시합니다.

세션은 Gradio State로 분리하고 최근 20회 문답만 보관합니다. 키 해제와 정상 탭 종료 시 저장된 키 참조를 제거하며, 상태에 30분 TTL과 삭제 콜백을 설정했습니다. 비정상 종료나 연결 끊김은 Gradio 세션 만료까지 정리가 지연될 수 있고, 이미 전송한 API 요청은 키 해제로 취소되지 않습니다. 키·예외 원문을 출력하지 않으며 조회 DB·원본 자료·환경 파일은 Gradio 파일 제공 경로에서 차단합니다. 데이터 적재는 기존 운영자 CLI에서만 수행합니다.

**이번 단계의 확인 범위 (2026-11-13):**

- 브라우저에서 전체 강좌 수 7,507건, 파이썬 검색 9행, 원문·SQL·표·키 없는 후속 질문의 차단과 기존 결과 보존을 확인했습니다.
- 실제 Gradio API와 로컬 모델에 연속 질문의 기대 재작성 문장 5개를 각각 전달해 정답 SQL과 비교했습니다. 결과는 전체 37행 → NCS 16행 → 2학기 6행 → 2024년 6행 → COUNT 6개로 일치했습니다. **Gemini가 실제로 이 문장들을 재작성했다는 검증은 아닙니다.**

- 실제 Gemini 호출은 수행하지 않았습니다. 화면에서 유효한 키를 입력한 뒤 기존 `GEMINI_MODEL`의 사용 가능 여부와 연속 질문 재작성 품질을 확인해야 합니다. 현재 모델명과 Docker·의존성·환경 설정은 변경하지 않았습니다.

### 로컬 모델로 단발 질문 조회

먼저 아래의 엑셀 적재 명령으로 DB를 준비한 뒤 실행합니다. Docker·패키지·환경 변수 설정은 기존 구성을 그대로 사용합니다.

```

- 원문, 실행한 SQL, 열·결과 행, 표시 제한 여부, 자동 안내, 생성 시간·토큰 수·PyTorch 피크 할당 VRAM을 JSON으로 출력합니다. 이 CLI는 독립 질문용이며 대화 기능은 Gradio 화면에서 사용합니다.
- `config.py`가 기존 환경 변수의 자료형·범위·고정 리비전을 검사합니다. `LocalSQLModel`은 최초 요청 또는 `load()` 시 한 번 로딩하며, 같은 인스턴스의 GPU 요청을 직렬화합니다. CPU 대체 실행이나 Unsloth 라이브러리는 사용하지 않습니다.
- 어댑터 모델 카드의 채팅 프롬프트 형식을 사용하고, 스키마·한국어 열 설명·실제 수집 기간·학과명·집계 기준을 전달합니다. 학과명과 따옴표로 지정한 과목명 키워드를 보존하도록 힌트를 추가합니다. 생성한 SQL을 규칙으로 고쳐 실행하지 않습니다.
- greedy decoding, 입력 2,048토큰·출력 256토큰·생성 60초의 기존 기본 설정을 사용합니다. 긴 입력을 자르지 않으며, 종료 토큰 없이 끊긴 출력이나 시간 초과 결과는 실행하지 않습니다. Transformers의 시간 제한은 현재 생성 단계를 마친 뒤 적용되는 제한으로, GPU 작업을 강제 종료하는 하드 타임아웃은 아닙니다.
- SQLGlot로 단일 SELECT, 모든 하위 쿼리의 테이블·열·함수를 검사합니다. 일반 CTE와 서브쿼리는 지원하지만 재귀 CTE·집합 연산·다중문·쓰기·외부 테이블은 거절합니다. 검증 실패에만 로컬 모델로 최대 한 번 재생성하며, DB 실행 오류와 시간 초과에는 재생성하지 않습니다.
- SQLite URI 읽기 전용 연결에 authorizer와 progress handler를 함께 적용합니다. 조회는 기본 5초 또는 약 500만 VM 명령에서 중단하며, 최대 200행과 잘림 확인용 1행만 읽습니다. 표시 제한을 SQL의 검색 조건에 추가하지 않습니다.
- 빈 질문·명백한 후속 질문·미지원 항목·수집 범위 밖의 학년도는 모델 호출 전에 안내합니다. 현재는 독립적인 질문 전용이며 생략 표현 판별은 보수적인 규칙입니다. 자연어 의도 판별 전체를 보장하지 않으며, Gemini 맥락 관리 단계에서 확장합니다.

**실제 검증 (2026-11-13):** README의 조건 조회·파이썬 검색·학과별 강좌 수·학과별 과목 수·연도별 NCS 비율과 전체 강좌 수, 총 6개 개발 예시가 정답 SQL 결과와 일치했습니다. 열 순서는 무관하게 비교하고 비율은 반올림 오차 0.01%p를 허용했습니다. 조건 조회 8행, 파이썬 검색 9행, 전체 강좌 수 7,507건입니다. 캐시가 준비된 상태의 로딩 약 14.9초, 질문별 생성 약 1.9~10.3초, PyTorch 피크 할당 VRAM 약 5.86GiB를 기록했습니다. 이 수치는 시스템 전체 GPU 점유량이나 일반 질문의 정확도가 아니며, 프롬프트 조정에 사용한 개발 예시의 확인 결과입니다.

쓰기·다중문·메타데이터 접근·확장 로딩·재귀 CTE 등 위험 SQL 18개 차단, 정상 조회·논리 조건·200행 제한·계산량 중단·검증 실패 시 재생성·실행 실패 시 재생성 없음도 일회성 검증했습니다. 모델은 실행 가능한 오답을 만들 수 있으므로 SQL을 함께 확인해야 하며, 별도 평가셋 검증은 후속 단계입니다.

```

- DB 경로는 기존 `COURSE_DB_PATH`를 사용하며 `--db`로 지정할 수도 있습니다.

- 모든 입력 검증이 끝난 뒤 하나의 트랜잭션에서 해당 학년도·학기·학년을 교체합니다. 다른 기간은 유지하며, 오류 시 기존 데이터 변경을 롤백합니다. `(year, semester, course_no)`를 기본 키로 사용합니다.
- 교수 가명은 교직원번호와 무작위 비공개 키를 이용한 HMAC으로 생성합니다. 같은 교직원번호는 같은 가명을 갖고, 동명이인은 번호로 구분됩니다. 교수 실명·교직원번호·대응표는 DB에 저장하지 않습니다.
- 키는 Git에서 제외된 `data/.professor-key`에 자동 생성합니다. **DB와 함께 비공개로 백업하고 배포 파일에는 포함하지 마세요.** 키가 없거나 기존 DB의 키와 다르면 적재를 중단합니다. 키는 역추적 방지를 위한 비밀값이며 가명 데이터도 익명 데이터로 간주하지 않습니다.
- 적재 결과에 실제 수집 범위, 학과 목록과 건수를 출력합니다. 현재 확인 범위는 2016~2026년, 각 1·2학기와 1·2학년, 44개 파일, 7,507행, 학과명 20개입니다. 학과명은 개편 전후 명칭을 통합하지 않습니다.

전체·부분 재적재의 결과 동일성, 원본 총건수 일치, 선행 0 보존, 잘못된 양식·학년·총건수·중복·수식 거절, 키 불일치 거절, DB 삽입 실패 시 롤백을 기존 컨테이너에서 일회성 검증했습니다. 자동 테스트 파일이나 테스트 의존성은 추가하지 않았습니다.

### 집계 기준과 조회 범위

- **강좌 수**는 분반을 포함한 행 수인 `COUNT(*)`로 집계합니다.
- **과목 수**는 중복 과목코드를 제외한 `COUNT(DISTINCT subject_code)`로 집계합니다.
- 학점, 교양·전공 구분, 수강 인원, 강의 시간, 강의실은 원본 자료에 없어 조회 대상에서 제외합니다. `major`는 전공명으로, 교양·전공 구분을 뜻하지 않습니다.
- 자료에 없는 항목이나 수집 범위 밖의 기간을 질문하면 조회 가능한 범위를 안내하도록 설계합니다.

## SQL 실행 및 개인정보 처리 방침

다음 제한을 구현할 계획입니다.

- SQLGlot로 단일 `SELECT` 조회인지 확인하고, 허용된 테이블과 함수만 사용하도록 제한합니다.
- 데이터베이스에 읽기 전용으로 연결하고, 실행 시간·계산량을 제한하며 결과는 최대 200행까지 표시합니다.
- SQL 검증 실패 시 한 번 재생성하고, 재시도에도 실패하면 안내 문구를 표시합니다.
- 교직원번호는 교수명 가명 처리 과정에서만 사용하고 조회 DB에 저장하지 않습니다.
- 교수명은 가명으로 변환하며, 원본 엑셀과 가명 대응표는 공개 저장소 및 배포 파일에서 제외합니다.
- Gemini API 키는 화면에서 가려서 입력받고, DB·코드·로그에 저장하지 않도록 처리합니다.
- Gemini에는 질문 재작성에 필요한 최소 맥락만 전달하고, 원본 엑셀·전체 DB·교수 실명·교직원번호는 전달하지 않습니다.
- 대화와 API 키는 사용자 세션 메모리에서만 관리하고, 키 해제·세션 종료 시 키를 폐기합니다.

## 배포 구상

접속용 정적 화면과 모델 조회 서버를 분리하는 구성을 계획하고 있습니다.

```text
사용자 브라우저
    ↓
Hugging Face Static Space
(조회 서버 주소 입력, 접속용 화면)
    ↓ @gradio/client
별도 GPU 서버의 Docker 컨테이너
(Gradio + Text-to-SQL 모델 + SQLGlot + SQLite)
    └─ 필요한 후속 질문만 Gemini API로 재작성 → 로컬 SQL 생성
```

Static Space에는 접속용 화면을 두고 모델과 DB는 별도 서버에서 실행합니다. 브라우저에서 해당 서버에 접근할 수 있어야 하며, CORS와 로컬 네트워크 접근 등 연결 조건은 후속 단계에서 확인할 예정입니다. 로컬 Gradio 화면 직접 접속은 구현·확인했습니다.

## 저장소 기본 설정

| 파일 | 용도 |
| --- | --- |
| `.gitignore` | 내부 문서(`docs/`), 원본 자료(`data/`, 엑셀 파일), 로컬 DB·모델·환경 설정·로그를 Git 추적 대상에서 제외 |
| `.gitattributes` | 텍스트 파일의 줄바꿈을 LF로 통일하고 Windows 명령 스크립트는 CRLF 사용 |
| `.editorconfig` | UTF-8 인코딩, 들여쓰기, 줄바꿈 등 편집 규칙 공유 |
| `.env.example` | DB 경로, 모델 리비전, 추론·SQL 제한, 접속 포트 등 환경 변수 예시 |
| `compose.yaml` | 공통 GPU 개발 환경의 빌드·실행 설정 |
| `requirements.txt` | Python 실행·GPU·개발 도구 의존성의 단일 목록 |
| `.dockerignore` | Docker 빌드에 필요한 파일만 허용 |
| `.devcontainer/devcontainer.json` | VS Code에서 공통 GPU 컨테이너에 연결하고 Python·Ruff 편집 환경 구성 |
| `.devcontainer/compose.yaml` | Dev Containers에서 인라인 빌드 대신 준비된 개발 이미지를 사용하도록 연결 |

Compose가 `.env`의 지정된 설정을 컨테이너 환경 변수로 전달합니다. 모델 추론과 SQL 제한 설정은 `config.py`에서 읽고 검증하며, `.env`는 Git에서 제외됩니다.
